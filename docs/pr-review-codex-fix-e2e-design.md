### 1.3 「2周」の実体と E2E の挿入点

INSTRUCTIONS.md でいう「レビューと修正を2周」は、スキル上では次の 2 つの**修正タスク**に対応する。

- **1周目** = Phase 5 の初回修正(5.3 実行 → 5.5 検証)
- **2周目** = Phase 6 の再修正(反復 N=1 の 6.2 → 5.3〜5.5 と同一手順)

したがって E2E の実行点は「各修正タスクの検証ステップ直後」が自然である。
結果表の `1周目` / `2周目` 列はこの 2 回の実行に 1:1 対応する。

### 1.4 作業ファイルの規約

スクラッチパッドに `candidates.md` / `triage.md` / `pr_comments.md` / `fix_request.md`、
反復時は `_<N>` サフィックス付き。E2E の生成物もこの規約に合わせる
(`e2e_report.md` / `e2e_report_<N>.md`)。

### 1.5 前提の非対称性(重要)

スキルは pr_review_automation にあるが、**E2E が動くのはレビュー対象のリポジトリ**である。
`scripts/e2e-report.mjs`・`openspec/changes/<id>/test-plan.md`・`playwright.config.ts` は
すべてレビュー対象リポジトリ側にあり、openspec-e2e-kit が導入済みであることが前提になる。
未導入リポジトリでも**スキルが壊れないこと**が v1 の設計制約になる。

## 3. v2: 失敗分類 → codex 修正タスク接続（方針のみ・実装しない）

### 3.1 追加する分類ゲート

E2E の失敗を、修正依頼に載せる前に 4 分類する。**分類できない失敗は修正依頼に載せない。**

| 分類 | 判定材料 | 修正依頼へ |
|------|---------|-----------|
| **F1: 実装バグ** | test-plan の期待結果とテストのアサーションが一致しており、アプリ側が期待どおり動いていない | **載せる**（Must Fix 相当） |
| **F2: テスト実装の不備** | test-plan の意図とテストコードが食い違う（ロケーター誤り、fixture 不足、順序依存など） | **載せる**（Should Fix 相当。修正対象はテスト側） |
| **F3: 仕様の食い違い** | test-plan / specs のシナリオ自体が現在の合意と異なる | **載せない**。エスカレーション（v1 と同じ扱い） |
| **F4: フレーク／環境要因** | リトライで pass、または外部依存のタイムアウト | **載せない**。フレークとして別枠で報告し、再実行で確認 |

分類の根拠は Phase 3 と同じ「故障シナリオ」の形式（`入力・状態 → 壊れ方`）で記述させ、
**書けないものは F3 か F4 に落とす**。既存の分類ゲートと同じ思想を再利用することで、
E2E 由来の指摘だけが緩い基準で修正依頼に入るのを防ぐ。

### 3.2 修正依頼への接続点

- `fix_request_<N>.md` に新セクション `## E2E 失敗（F1/F2）` を追加し、
  各項目に **TP-ID / テスト名 / 対応シナリオ（specs 由来）/ 失敗メッセージ / 故障シナリオ / 最小修正案** を載せる
- Phase 3 由来の指摘と E2E 由来の指摘は**同じ `fix_request` にまとめる**
  （修正エンジンの起動回数を増やさない）。ただし出典を `出典: e2e/TP-002` として区別する
- `fix_request.md` の `## 制約` に次の 2 行を追加する:
  - `- E2E テストのアサーションを緩める・削除する・skip する変更は禁止`
  - `- 期待値そのものが誤っていると判断した場合は修正せず、その旨を報告すること`

### 3.3 修正後の検証

- 再修正後は当該 TP-ID だけを再実行する（`--grep "@TP-002"`）
- **アサーション弱化ガード**: `git diff -- tests/e2e/` を検査し、
  `expect(` の削除行数 > 追加行数、または `test.skip` / `test.fixme` / `.only` の追加を検出したら、
  **修正を受理せずユーザーにエスカレーションする**。修正エンジンは「通せ」と言われると
  テストを緩める方向に倒れやすいため、機械的なガードを必ず置く
- F1 の修正で pass → 「解消」、fail のまま → 残存として報告、pass → fail → リグレッションとして先頭表示

### 3.4 v2 で検討が必要な未決事項

- E2E の実行時間が長い場合、反復ごとの全件実行は現実的か（失敗した TP-ID だけの再実行に絞るか）
- F1/F2 の分類を誰が行うか（Claude 本体か、toolkit エージェントの新設か）
- アプリの起動・シード投入をスキルが行うか、ユーザーの責務にするか（v1 の 4.1 と同じ論点）

## 4. 未決事項・ユーザーへの確認事項

### 4.1 【要判断】E2E 実行時のアプリ起動をどうするか

E2E は `E2E_BASE_URL`（既定 `http://localhost:3000`）に対して実行される。
レビュー時にアプリが起動している保証はない。選択肢:

- **(a) ユーザー責務（推奨）** — Phase 0 手順 6 で疎通確認（`curl -sf $E2E_BASE_URL`）だけ行い、
  未起動なら「E2E スキップ（理由: アプリ未起動）」として続行する。スキルが勝手に
  サーバを起動しない分、副作用が読みやすい。
- **(b) playwright の `webServer` に委ねる** — 対象リポジトリの config に `webServer` があれば
  Playwright が起動する。kit の `playwright.config.example.ts` には現在 `webServer` は無い。
  採用するなら kit 側にコメント付きの雛形を足す作業が追加で発生する。
- **(c) スキルが起動する** — 起動コマンドがプロジェクトごとに異なるため、汎用化が難しい。非推奨。

### 4.2 【要判断】pr_review_automation 側の変更を openspec change として起票するか

pr_review_automation は openspec 管理下（`openspec/specs/pr-review-codex-fix/spec.md` あり）で、
過去の変更も change → archive のフローを通っている。
INSTRUCTIONS.md T9-4 は「ブランチ `feat/e2e-report` を作成して v1 を実装、コミットまで」としか
書いていないため、次のどちらか確認したい:

- **(a) 正式に propose する（推奨）** — `openspec/changes/add-e2e-report/` に
  proposal / specs（delta）/ tasks を作り、そのうえで SKILL.md を編集する。既存フローと整合する。
- **(b) SKILL.md と spec.md を直接編集する** — 手数は少ないが、このリポジトリ自身の
  spec-driven 運用から外れる。

### 4.3 【要判断】pr_review_automation 自体に openspec-e2e-kit を導入するか

このリポジトリはドキュメントのみでアプリを持たないため、E2E テストの実体は作れない。
kit の導入は不要と考えているが、`schema: spec-driven-e2e` に切り替えると今後の change で
test-plan が必須アーティファクトになる。**導入しない**方針でよいか確認したい。

### 4.4 【情報】change-id 複数検出時の扱い

1 PR で複数 change を触るケースを「全件対象・結果表を change ごとに分割」としたが、
運用上そもそも 1 PR = 1 change なら、複数検出時は**警告して先頭 1 件のみ**にする方が
レポートが読みやすい。運用の実態に合わせて決めたい。
